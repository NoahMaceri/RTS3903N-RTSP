# Yi Camera — Cloud Protocol Reverse Engineering Notes

Static analysis of the user's own flash dump. RTS3903 MIPS, Linux 3.10, uClibc.
Ghidra headless exports under `../../Decompiled source/` (see its README for the apps/ sdk/ kernel_modules/ tools/ layout). Facts cite `function @ addr` / exact strings; inferences are labelled **inferred**. Device secrets described by role only.

## 1. cloudAPI internals

`/backup/cloudAPI` is the single HTTP/TLS client that every daemon shells out to. Binary at `../../Decompiled source/apps/cloudAPI/`.

### 1.1 HTTP / TLS stack (observed)
- **DT_NEEDED**: `libpthread.so.0, librt.so.0, libc.so.0` — **no** libcurl/libssl shared deps.
- libcurl **and** CyaSSL (old wolfSSL) are **statically linked in**. Evidence: exported/defined symbols `CyaSSL_*`, `HmacSetKey`, `Sha256Hash`, `Md5Hash`, `Base64_Encode/Decode`, `RsaSSL_VerifyInline` (dynsym.tsv); strings `curl_easy_perform() failed: %s`, `# This file was generated by libcurl!`, CyaSSL internal strings (`ProcessReply`, `App data buffer error, malicious input?`, `RSA buffer error...`).
- The request builders call thin wrappers `FUN_004126c8` (= curl_easy_setopt), `FUN_004126f8` (curl_easy_perform), `FUN_00412670` (easy_init), `FUN_004128e4` (cleanup). Option numbers are stock libcurl CURLOPT_* values: `0x2712`=URL(10002), `0x40`=SSL_VERIFYPEER(64), `0x51`=SSL_VERIFYHOST(81), `0x2751`=CAINFO(10065), `0x2f`=POST(47), `0x271f`=POSTFIELDS(10015), `0x2727`=HTTPHEADER(10023), `0x36`=UPLOAD(54), `0x4e2c`=READFUNCTION(20012).

### 1.2 Argument parsing → opcode dispatch (observed)
- `main @ 0x0040376c` (size 9796) parses long-form flags (`-c`, `-key`, `-keySec`, `-url`, `-uid`, `-did`, `-token`, `-filename`, `-EventTime`, `-EventStat`, `-pic_url`, `-video_url`, `-pic_pwd`, `-video_pwd`, `-heart_time`, `-p2p_status`, `-suffix`, `-type`, `-sub_type`, …).   - 1–11 legacy kuaipan.cn OAuth ops; 12 register; 128–135 legacy login/heartbeat/event/reset
  - **136** syntime, **137** bindkey(qr_bind), **138** login_v4(on_line), **139** reset_v4, **140** need_upgrade, **141** tnp_on_line, **142** get_dev_info, **143** check_region, **144** update_upgrade_log, **145** force_upgrade, **192** report_tnp_on_line_status, **193** report_cloud_alarm_status, 300 multi_download, 301 get_firmware_md5, 302/303/304 update_event(_v4)/add_device, **305/306** gen_presigned_url(_v5), 310 apply_sn, **311** check_did, **312** get_ststoken, 410 qiniu_upload, **411** event_upload, 412 yi_info_report, **413** log_upload, 414 upload_data.
- Dispatch: opcode compared and the matching handler called (per-opcode functions `FUN_0040b080`, `FUN_0040b230`, … seen in main at 0x403xxx).

### 1.3 Request authentication / signing scheme (observed — the core finding)

Two distinct families:

**(A) xiaoyi IPC API (opcodes 136–145, 304):** query-string HMAC. Each handler builds a fixed-order base string, signs it, and prepends `hmac=`.

Signer `FUN_0040965c(base, 0, key, out)`:
1. `FUN_00408b74(key, keylen, base, baselen, dig)` = **HMAC-SHA1** (confirmed: SHA1 IVs `0x67452301,0xefcdab89,0x98badcfe,0x10325476,0xc3d2e1f0`; ipad `0x36`, opad `0x5c`; 20-byte digest). `key` = the `-keySec` argument (developer secret).
2. `FUN_00406834(...)` between the two steps is **only a debug hexdumper** gated on `fopen("/home/tmpfs/API_DEBUG")` — does **not** modify the digest.
3. `FUN_00408ff4(dig, out, 0x14)` = **Base64_Encode** (uses base64 alphabet table `_fdata`, `=` padding) of the 20-byte digest.

So:
```
base = "seq=9&uid=<UID>&timestamp=<unixtime>[&<extra ordered params>]"
hmac = Base64( HMAC_SHA1( key = keySec, msg = base ) )          # 20-byte digest -> 28-char b64
url  = "<endpoint>?hmac=<hmac>&" + base
```
Params are emitted in a **fixed hard-coded order per opcode (NOT sorted)**; no nonce in family (A). Example bases (handler → string):
- 136/138/139 `FUN_0040b080`: `seq=9&uid=%s&timestamp=%u`
- 137 bindkey `FUN_0040b230`: `seq=9&uid=%s&bindkey=%s&timestamp=%d`
- 142/311 `FUN_0040b3dc`: `seq=9&uid=%s&timestamp=%d`
- 140/145 need_upgrade `FUN_0040bbfc`: `seq=9&uid=%s&version=%s&timestamp=%u`
- 138 login full `FUN_0040abc4`: `seq=9&uid=%s&password=%s&version=%s&model=0&port=0&mac=%s&packetloss=%s&p2pconnect=%s&p2pconnect_success=%s&tfstat=%s&timestamp=%u` plus `&ext_info={"p2p_encrypt","ssid","mac","ip","signal_quality","ap_mode"}` (URL-encoded).

`uid`/`did` is **not** sent in the clear: `FUN_00409468(did, did, out)` sets a 16-byte **AES-128** key (`FUN_00496af4(ctx, key, 0x10,...)`), AES-ECB encrypts (`FUN_0049729c`) then **hex-encodes** (`%02x` loop) — producing the `uid=` value. The `password=` field (login/heartbeat) is a second transform `FUN_00409538(bindkey, did, out)` (bindkey+did → token). Both described by role; values not reproduced.

**(B) Legacy kuaipan.cn cloud (opcodes 1–11):** OAuth 1.0a, `oauth_signature_method=HMAC-SHA1`, params **sorted** (`oauth_consumer_key&oauth_nonce&oauth_signature_method&oauth_timestamp&oauth_version…`), signature base `%s&%s&%s` (method&url&params, `FUN_004091f4`), nonce `FUN_0040974c` (`rand()%9999`), timestamp `FUN_004097cc`. `qsort` import is used here. These endpoints (`openapi.kuaipan.cn`, `api-content.dfs.kuaipan.cn`) are **dead legacy code** — the live firmware uses family (A); the `-url` for xiaoyi is supplied by the `cloud` daemon, not hard-coded in cloudAPI.

### 1.4 TLS certificate verification (observed — mixed)
- **xiaoyi API calls (136–145, etc.): verification ON.** Every handler sets `VERIFYPEER=1`, `VERIFYHOST=2`, `CAINFO="/backup/ca/ca.crt"`.
- **CA bundle** `rootfs_backup/ca/ca.crt` = **GlobalSign Root CA** (single cert, self-signed, valid 1998–2028). Companion `rootfs_backup/ca/gd_bundle-g2-g1.crt` = GoDaddy G2/G1 bundle. `rootfs/etc/ssl/` only holds stock OpenSSL `misc/` helper scripts + empty `certs/` — not used by cloudAPI. Effectively a **pinned 1–2 root CA set**.
- **Event/media upload (opcode 411, `FUN_0040e190`): verification OFF.** Sets `VERIFYPEER=0` and `VERIFYHOST=0`, `UPLOAD=1` (HTTP PUT with READFUNCTION body callback) to the server-supplied presigned `-url`. **The TLS cert of the OSS presigned endpoint is not validated.** On HTTP 200 it prints the stub marker `{"accessKeyId":"access_key_id"}` that the cloud daemon greps for (not a real credential).

The QR/AP decode and Wi-Fi credential capture is done by **rmm/dispatch** (separate agent's scope); the bind key reaches `cloud` as the `-key` value. Config/state shared via `/tmp/mmap.info` (mmap) and dispatch IPC; `api_server` persisted to flash through dispatch (not written directly by cloud).

## 3. Event / media upload path

### 3.1 Cloud-side sequence (observed, `FUN_00405428` "yi_motion_push" @ 0x405428)
Trigger types: motion (`/tmp/motion.jpg`,`/tmp/motion.mp4`), babycry, abnormal_sound, voice-call (`FUN_00405f58`: `/tmp/vc_record.mp4`→`.crypt`).
1. `cloudAPI -c 306 -url %s/v5/alert/gen_presigned_url -uid %s -keySec %s -type %d -sub_type %d -suffix %s -time %d`.
2. Parse response: for each of pic & video extract **`"url"` (presigned PUT URL) and `"pwd"` (per-event encryption password)** — `FUN_0040b9ac(..,"\"url\"",..)` / `..,"\"pwd\"",..`. **The password is returned by the server, per event**, not generated on-device.
3. `cloudAPI -c 304 -url "%s/v4/alert/event" ... -pic_url -video_url -pic_pwd -video_pwd -type -sub_type` (`FUN_004037d4`) — the event metadata incl. the two passwords is posted to the alert API; success = JSON `"code"==20000`; reply `"ipcSetTime"` adjusts next-event timing.
4. **Encrypt-if-pwd-present then upload**: if `pwd != ""`, `FUN_00404fd4` runs `system("/home/app/crypt_file -e <in> <out> <pwd>")`, else the raw file is used. The (encrypted) file is PUT to the presigned `url` via `FUN_00403ad8` → `cloudAPI -c 411 -url "<presigned>" -filename <file>`; on success the source file is `rm`'d.

So: **motion → 306 (get presigned url + password) → 304 (report event + passwords) → crypt_file -e → 411 PUT to OSS**. Encryption is conditional on the server supplying a non-empty `pwd`.

### 3.2 crypt_file (observed)
- `crypt_file` DT_NEEDED: `librt, libc` only; **CyaSSL AES statically linked** (`AesSetKey`, `AesCbcDecrypt` strings). No OpenSSL.
- `main @ 0x400960`, `argc==5`, usage `%s [-e/-d] [src_file] [dst_file] [key]`. Modes `-e`/`-d`/`-ee`/`-dd`; the "ext" flag is a **no-op** (the 6th arg is never read — `-ee`≡`-e`, `-dd`≡`-d`).
- **Cipher = AES-128-ECB** (observed): `FUN_00400f94` core; chunk fns `FUN_00400da0`(enc)/`FUN_00400ea8`(dec) set a 0x10-byte key with no IV, process each 16-byte block independently (no chaining). Key = **first 16 ASCII bytes of argv[4] (the password), zero-padded**. Output = 4-byte LE original-length header + AES-ECB of zero-padded body. **No IV, no MAC/integrity, zero padding, plaintext length in clear header.**
```
crypt_file -e src dst pwd:
  k = (pwd ++ zeros)[0:16]            # AES-128 key = first 16 bytes of ASCII password
  out  = LE32(filesize(src))
  out += AES128_ECB_Enc(k, zero_pad_16(src_bytes))
```
- **Key source**: the per-event `pwd` from the 306 response (event path), or the STS `tsSecret` (oss index-JPG path). Not hardcoded.

### 3.3 oss binary — continuous cloud recording (HLS), separate from event alerts (observed)
- DT_NEEDED: `libcrypto.so.1.0.0, libssl.so.1.0.0, libpthread, libm, librt, libc`. Statically links **Aliyun OSS C SDK `aliyun-sdk-c/0.0.7`**, **Tencent COS C SDK `cos-sdk-c/5.0.3`**, libcurl, APR, CyaSSL, libxml2.
- Credentials via `cloudAPI -c 312 /v4/ipc/STSToken` (`get_ststoken FUN_00409520`): parses `ossBucketName, tsSecret, ossObjPrefix, accessKeyId, tsNonce, ossEndPoint, ossCallback, accessSecurityToken, accessKeySecret, m3u8ObjKey, memo*`.
- Uploads AES-128-**CBC**-encrypted `.ts` segments (OpenSSL `AES_cbc_encrypt`, PKCS#7 padding) with **hardcoded IV `0x61616161`×4 = "aaaa…"** (`DAT_0056bbb0`, set in `get_ststoken`), key = `hexdecode(tsSecret)[0:16]`. Index `.jpg` encrypted via `crypt_file -ee ... <tsSecret>`. m3u8 playlist. HLS `EXT-X-KEY AES-128` style.
- OSS request auth: `HMAC-SHA1(accessKeySecret, StringToSign)` → base64 → `Authorization: OSS <ak>:<sig>`, `x-oss-security-token: <STS token>`, `x-oss-date`, `Content-MD5` (`FUN_0041a7d4`/`FUN_0041992c`/`FUN_0041a568`). **oss SDK transport also disables TLS verify** (VERIFYPEER=0/VERIFYHOST=0 in `FUN_0041fff4`/`FUN_00417864`). Endpoint is server-supplied (no hardcoded `oss-cn-*`); `oss_fast`/`oss_lapse` roles via argv[0].

### 3.4 Division of labour (observed)
| Role | Event alerts | Continuous recording |
|---|---|---|
| Get URL/creds | `cloud`→`cloudAPI 306` (presigned URL + per-file pwd) | `oss`→`cloudAPI 312` (STS AK/SK/token, bucket, endpoint, tsSecret) |
| Encrypt | `crypt_file -e` with server pwd (AES-128-ECB) | `oss` in-proc AES-128-CBC (IV "aaaa…") for .ts; `crypt_file -ee` + tsSecret for index .jpg |
| Upload bytes | `cloudAPI 411` libcurl PUT (TLS NOT verified) | `oss` via Aliyun/Tencent SDK (OSS HMAC-SHA1 auth) |

- **413 log_upload** (`cloudAPI FUN_0040e030`): multipart POST, fields `devid`/`devlog`, TLS verify OFF; cloud checks `"UploadLog.Success"`.
- **414 upload_data** (`cloudAPI FUN_0040e45c`): CA-verified GET returning `"uploadUrl"`; record file then PUT via **411 unencrypted** (`cloud yi_push_rcd_file FUN_00405040`, then `rm -f /tmp/recorddata/rcd_*`).
- **inferred**: the server generates each event `pwd` and receives it back via 304, so the vendor holds every event key — encryption protects the object store, not against the vendor. 306/312/414 (which carry the URL/pwd/STS secrets) ARE CA-verified; only the bulk-data PUTs (411/413 + oss SDK) skip verification.

## 4. OTA / firmware update

### 4.1 need_update (opcode 145) request/response (observed, cloud `need_update FUN_00402a0c`)
- Request: `cloudAPI -c 145 -url "<base>/vmanager/ipc/firmware/upgrade/silent" -did %s -sname %s -version %s` (@0x40e8b8). (cloudAPI signer side: `FUN_0040bbfc` signs `seq=9&uid=%s&version=%s&timestamp=%u`.)
- Response fields parsed (`FUN_0040b8cc`): **`needUpdate`** (@0x40e928, must equal ref string), **`downloadPath`** (@0x40e93c → URL buffer), **`md5Code`** (@0x40e94c → md5 buffer). No `version` read from body.
- Launch (`do_update_ex FUN_00402988`): `killall upgrade_firmware; rm -f /tmp/sd/home_r10 /tmp/sd/home_r10m; /home/app/upgrade_firmware "<downloadPath>" "<md5Code>" &`.

### 4.2 Download + flash flow (observed)
- **Path A (cloud-triggered): `upgrade_firmware`** (main @0x400910, `Usage: %s [URL] [MD5]`). Downloads `<downloadPath>home_r10m` via `cloudAPI -c 300 ... -filename /tmp/loadtmp/firmware_m.bin` (`get_upgrade_file FUN_00400ff0`), md5-checks it vs argv MD5 (`FUN_00400d60`), `mv` to `/tmp/update/firmware_m.bin`, then `system("/backup/script/update.sh /tmp/update/firmware_m.bin")`, then `killall watchdog` + `reboot`.
- **Path B (script-triggered): `download_upgrade`** (main @0x401270) reads `/backup/upgrade_conf` (`g_upgrade_conf =%s %s %s %s`) for URL+MD5, md5-checks (`md5_check_file @0x401cb0`).
- **update.sh**: picks firmware (argv[1] | SD `/tmp/sd/home_r10m` | downloaded); version gate = first 24 bytes (`dd bs=24`) vs `/home/homever`; `decpkg.sh <fw> firmware.tgz`; `tar xf`; require `home.bin`; `update_file backup`; `umount -l /home`; **`/backup/mtd_img 4 home.bin`** (writes /dev/mtd4, **no integrity check** in mtd_img).

### 4.3 Package format + RSA (observed, decpkg.sh + rsa_pub_dec main @0x400820)
Layout: `[0:24]` plaintext version header · `[24:1048]` = **4 × 256-byte RSA ciphertext blocks** · `[1048:EOF]` tgz payload tail.
- `rsa_pub_dec enc dec`: input must be exactly 0x400 (1024) bytes; decrypts four 0x100 blocks via `RSA_public_decrypt(flen=0x100,...,flag=_fdata)` (`FUN_00400d0c`), each must return **0xf5 = 245** bytes → 980 bytes out.
- **Public key**: a **2048-bit** RSA key embedded as a `-----BEGIN PUBLIC KEY-----` SubjectPublicKeyInfo PEM literal inside `rsa_pub_dec` main (loaded via `BIO_new_mem_buf`+`PEM_read_bio_RSA_PUBKEY`, `FUN_00400c80`). Uses libssl/libcrypto .so.1.0.0 (not CyaSSL). Key bytes not reproduced.
- **Padding**: 245 = 256−11 ⇒ **PKCS#1 v1.5** (`_fdata` = RSA_PKCS1_PADDING). This is a raw public-key decrypt, not a proper signature-verify API.
- Decrypted 980 bytes → `md5`(32B hex) + `pwd`(32B) + `dst_ver`(24B) + 892 bytes **prepended** to firmware.tgz; then `src[1048:]` **appended**.

### 4.4 CRITICAL — payload integrity is NOT bound to the RSA-signed md5 (observed)
- decpkg.sh extracts `$md5` and `$pwd` from the RSA block but **only `echo`s them — never used again**. The RSA-recovered `md5` is dead.
- The **only** RSA-gated check is `version1 (24B header) == dst_ver` (decpkg.sh:39).
- update.sh **never computes md5 of firmware.tgz**; its `md5sum` calls (in `update_file`) are per-file change-detection for `/backup`, unrelated to the signed md5.
- RSA signature validity does authenticate: the version header, and the **first 892 bytes** of the tgz (bytes 88..979 of the signed block). Everything from file offset **1048 to EOF (the bulk of the tgz) is unsigned and unverified**.
- Download paths additionally md5-check the file vs the **cloud-supplied `md5Code`** — but that md5 is attacker-supplied over the same channel and differs from the RSA md5. The **SD-card path (`/tmp/sd/home_r10m`) bypasses download_upgrade entirely**, so only the payload-blind RSA block gates it.
- **inferred (exploit surface)**: a package reusing a legitimately-signed 1048-byte prefix (version + RSA block) from any genuine Yi firmware, followed by an arbitrary tgz tail whose first 892 bytes match the donor, passes decpkg.sh and is flashed unverified. Practical feasibility of crafting a valid tar/gzip around a fixed 892-byte prefix not dynamically confirmed.

## Key security observations (summary)
1. **xiaoyi API signing** = `Base64(HMAC-SHA1(keySec, fixed-order-querystring))`; TLS CA-pinned (GlobalSign/GoDaddy) with VERIFYPEER/HOST on. Solid for the control plane.
2. **Bulk media uploads skip TLS verification** (cloudAPI 411 PUT, 413 log POST, oss SDK transport) — MITM can capture/redirect blobs. Mitigated only by payload AES, not endpoint auth.
3. **Event media AES-128-ECB** with a server-issued per-event password → vendor holds all keys; ECB + no MAC + zero padding + plaintext-length header is weak.
4. **oss .ts uses a hardcoded IV "aaaa…"** (AES-128-CBC) — IV reuse across all segments/devices.
5. **OTA signature does not cover the payload**: the RSA-signed md5 is extracted and discarded; only the 24-byte version and first 892 bytes of the tgz are signed; the tgz tail (offset 1048→EOF) and the flashed `home.bin` are unverified. SD-card update path bypasses even the cloud md5Code check.

## Open questions
- Exact AES-ECB key derivation for the `uid` transform (`FUN_00409468`) and the login `password` transform (`FUN_00409538`) — derived from did/bindkey; not fully traced to constants.
- Whether a working tar/gzip can be crafted around the fixed 892-byte signed prefix to weaponize the OTA gap (packaging feasibility, needs dynamic test).
- `oss` plain-HTTP possibility (`http://%s:%d/%s` present) not confirmed.
- QR/AP-mode decode + Wi-Fi credential capture lives in rmm/dispatch (separate agent) — how the bind key and Wi-Fi creds physically arrive is out of scope here.
